# Obelisk — архитектура

Obelisk — VPN-клиент для OpenWrt, который одновременно управляет двумя ядрами,
Xray-core и sing-box, и сам решает, какое из них способно нести конкретный узел
подписки. Ядра не патчатся и не линкуются внутрь: Obelisk запускает стоковые
бинарники и кормит их сгенерированной конфигурацией.

## 1. Почему Go

Целевое железо — от Raspberry Pi 4 до бюджетных роутеров, поэтому язык выбирался
по трём критериям: статический бинарник без рантайма, кросс-компиляция под все
архитектуры OpenWrt одной командой, и предсказуемый расход памяти.

Go даёт всё три. Один и тот же исходник собирается под `amd64`, `arm64`, `armv7`,
`mipsle` и `mips` с `CGO_ENABLED=0` — то есть тот же бинарник, что лежит в
Docker-образе, кладётся в ipk-пакет без единого изменения. Это прямо влияет на
план релизов: Docker первым, нативный ipk вторым, но **кодовая база одна**.

Про Docker стоит сказать честно: он не даёт универсальности на слабом железе.
На роутере с 16–32 МБ флеша Docker физически не встаёт. Универсальность здесь
даёт статическая линковка, а Docker даёт другое — изоляцию зависимостей и
возможность обновлять ядра, не пересобирая клиент. Ради этого он и берётся.

Фронтенд — HTML, CSS и обычный JavaScript без этапа сборки; вшивается в бинарник
через `embed`, чтобы веб-интерфейс не требовал отдельного веб-сервера на роутере.

## 2. Топология: sing-box впереди, Xray сзади

Ключевое решение всего проекта. Оба ядра не могут владеть системным инбаундом
одновременно, поэтому роли разделены жёстко:

```
                    ┌──────────────────────────────────────────┐
   LAN-клиенты ────►│  sing-box  (front core)                  │
                    │  • tun / tproxy / redirect / mixed       │
                    │  • дерево маршрутизации, split-tunnel    │
                    │  • DNS: split, FakeIP, hijack            │
                    │  • группы selector / urltest             │
                    └───┬──────────────────────────────┬───────┘
                        │ узлы, которые несёт sing-box │ узлы Xray
                        ▼                              ▼
                  напрямую в интернет      127.0.0.1:241xx  (SOCKS5)
                                                       │
                                           ┌───────────▼──────────┐
                                           │  Xray  (backend core)│
                                           │  1 SOCKS-инбаунд     │
                                           │    на каждый узел    │
                                           └───────────┬──────────┘
                                                       ▼
                                                 в интернет
```

**Почему sing-box впереди.** У него принципиально богаче инбаунды (`tun` с
`auto_route`, `tproxy`, `redirect`), есть rule-set'ы, FakeIP и sniffing как
действие маршрутизации. Всё это нужно ровно один раз и в одном месте.

**Почему по одному порту на узел Xray.** Xray маршрутизирует по тегу инбаунда,
на который пришло соединение. Выделенный loopback-порт на каждый узел делает
передачу однозначной: ничего не нужно сниффить повторно и никакие метаданные не
обязаны пережить переход между процессами.

**Цена перехода.** Узел на Xray стоит лишнего копирования в user space и второго
процесса в памяти. Поэтому политика по умолчанию (`model.DefaultPolicy`) при
прочих равных оставляет трафик в sing-box, и Xray вообще не запускается, если ни
один узел его не требует (`Plan.NeedsXray`).

**Петля маршрутизации.** Соединение, которое Xray открывает к удалённому серверу,
само попадает под прозрачный перехват фронтового ядра и уходит обратно в тоннель,
который пытается установить. Обход: Xray ставит `SO_MARK` на свои исходящие
сокеты (`streamSettings.sockopt.mark`, по умолчанию `0x4f42`), а слой firewall
пропускает помеченные пакеты мимо перехвата. Это обязательная часть контракта
между `internal/core` и будущим `internal/netfw`.

## 3. Матрица возможностей

`internal/model/capability.go` — единственное место в проекте, которое знает, что
именно умеет каждое ядро. Когда ядро обзаводится новым протоколом, меняется
только этот файл.

| Возможность | Xray | sing-box | Кто несёт |
|---|:--:|:--:|---|
| VLESS / VMess / Trojan / Shadowsocks | ✔ | ✔ | по политике |
| SOCKS / HTTP / WireGuard | ✔ | ✔ | по политике |
| Hysteria, Hysteria2, TUIC, AnyTLS, ShadowTLS, SSH | — | ✔ | только sing-box |
| Транспорт XHTTP, mKCP | ✔ | — | только Xray |
| HTTP-камуфляж поверх raw TCP | ✔ | — | только Xray |
| VLESS Encryption (постквантовая) | ✔ | — | только Xray |
| SIP003-плагины Shadowsocks (obfs-local, v2ray-plugin) | — | ✔ | только sing-box |
| Транспорт QUIC | — | ✔ | только sing-box |
| ShadowsocksR | — | — | никто |

Разрешение выбора идёт от частного к общему: закрепление узла пользователем →
единственное способное ядро → политика по протоколу → эвристика XTLS Vision →
умолчание. Узел, который не может нести никто, не роняет план — он попадает в
`Plan.Rejected()` с человеческой причиной. «В вашей подписке 4 узла SSR, которые
не поддерживает ни одно ядро» несравнимо полезнее молча укоротившегося списка.

## 4. Структура

```
cmd/obelisk/            CLI и (далее) демон
internal/model/         нормализованная модель узла + матрица возможностей
internal/subs/          парсеры подписок: URI, base64, Clash YAML, sing-box JSON
internal/core/          supervisor процессов, планировщик топологии
internal/core/xray/     генерация конфигурации Xray
internal/core/singbox/  генерация конфигурации sing-box
```

Направление зависимостей строго одностороннее: `subs` и `core` знают про `model`,
про друг друга — нет. Ничто за пределами `subs` не обязано знать, как выглядит
`vmess://`, и ничто за пределами `core/xray` — как выглядит JSON Xray.

### Модель узла

`model.Node` — плоская структура с опциональными блоками под конкретные
протоколы. У неё есть `Fingerprint()` — кортеж полей, реально определяющих, куда
и как идёт трафик. Имя в него намеренно не входит: панель переименовывает узлы
между обновлениями подписки, и `ID`, построенный на отпечатке, позволяет
сохранять историю задержек и пользовательские закрепления через обновления.

### Парсеры

Написаны намеренно снисходительными. Подписки в природе производятся десятками
панелей с несогласованным экранированием, разными алфавитами base64 и
необязательным паддингом; парсер, следующий спецификации, отвергал бы ссылки,
которые принимает любой реальный клиент. Правило: принимать всё, что понимается
однозначно, и отвергать только то, из чего получился бы неработоспособный узел.

Поддержано: `vless`, `vmess` (оба диалекта), `trojan`, `ss` (SIP002 / legacy /
SS2022), `ssr`, `hysteria`, `hysteria2`, `tuic`, `anytls`, `socks`, `http`,
`ssh`, `wireguard`; агрегаты — base64-списки, Clash/Clash.Meta YAML, sing-box
JSON; заголовки `subscription-userinfo`, `profile-title`,
`profile-update-interval`.

## 5. Режимы перехвата

Все три генерируются из одного и того же дерева маршрутизации — различается
только инбаунд, поэтому режим переключается на лету без пересборки правил.

- **TUN + auto_route** — полный L3-перехват, включая UDP, QUIC и ICMP. Требует
  `/dev/net/tun` в контейнере. Умолчание.
- **TPROXY** — TCP и UDP через nftables-метки и policy routing. Легче по
  ресурсам, традиционный выбор на роутерах.
- **REDIRECT** — только TCP через NAT. Максимальная совместимость, но UDP (а
  значит QUIC) приходится блокировать, а не проксировать.
- **proxy** — только mixed SOCKS/HTTP, ничего не перехватывается.

## 6. Ядра остаются независимыми

Ни Xray, ни sing-box не вкомпилированы в Obelisk и не слинкованы с ним. Это
отдельные исполняемые файлы, которые Obelisk запускает как дочерние процессы и
которым передаёт сгенерированный конфиг. Следствие ровно то, ради которого так
сделано: **обновление ядра — это подмена файла, а не пересборка клиента.**

`internal/cores` владеет этой подменой:

- определяет установленную версию, спрашивая сам бинарник (`xray version`,
  `sing-box version`), а не доверяя своему файлу состояния — ядро могли
  подменить руками, откатом или через opkg;
- находит нужный ассет релиза под конкретную архитектуру. Проекты называют
  ассеты по совершенно разным системам — Xray по разрядности и ревизии ARM
  (`Xray-linux-arm64-v8a.zip`), sing-box по именам архитектур Go с версией в
  имени (`sing-box-1.13.16-linux-arm64.tar.gz`) — оба маппинга лежат в одном
  файле, `catalog.go`;
- ставит атомарно: скачать → проверить → распаковать → **запустить и спросить
  версию** → подвинуть старый бинарник в `.bak` → переименовать новый на место.
  Проверка запуском ловит скачанный не под ту архитектуру ассет сразу, а не в
  худший момент;
- умеет откатываться. На роутере это единственный путь восстановления: то, что
  только что сломалось, и есть единственный выход в сеть.

**О версиях.** Xray перешёл на календарные версии: актуальная — `v26.3.27`, а не
`v1.8.x`. sing-box остаётся на семантических, актуальная — `v1.13.16`. Теги несут
`v`, а бинарники сообщают о себе голое число, поэтому сравнение идёт через
нормализацию.

**О доверии.** Xray публикует `.dgst` рядом с каждым архивом, и Obelisk сверяет
SHA-256. **sing-box не публикует контрольных сумм вообще**, поэтому его загрузка
достоверна ровно настолько, насколько достоверно TLS-соединение, по которому она
пришла. Obelisk показывает это состояние как `unverified`, а не выдаёт за
проверенное. Хеш записывается в любом случае — это не делает загрузку надёжнее,
но позволяет позже заметить, что файл на диске изменился.

**Уважение к чужим установкам.** Порядок поиска: сначала каталог, которым владеет
Obelisk, затем `/usr/bin`, `/usr/local/bin`, `/opt/bin`, затем `PATH`. Ядро,
поставленное через opkg, используется как есть и никогда не перезаписывается:
обновление кладёт новую копию в свой каталог и *перекрывает* системную, о чём
прямо сообщает. Иначе последующий `opkg upgrade` выглядел бы как не сработавший.

Установка под чужую архитектуру (`-target linux/arm64`) позволяет подготовить
ядра на рабочей станции или в CI для роутера, куда они поедут файлами. Именно
этим Docker-сборка и наполняет образ — тем же кодом, который потом будет
обновлять ядра на живой системе.

## 7. Маршрутизация: что уходит в туннель

`internal/routing` решает главную задачу сплит-туннелирования — какие домены и
адреса идут через VPN, а какие мимо. Точка входа одна: `ParseEntry` принимает
строку и сам разбирается, что это.

```
https://www.youtube.com/watch?v=... → домен www.youtube.com и всё под ним
*.googlevideo.com                   → googlevideo.com и всё под ним
142.250.0.0/15                      → подсеть
142.250.150.100                     → адрес (как /32)
torrent                             → ключевое слово в любом домене
geosite:google                      → внешний список
/^ads?\..*/                         → регулярное выражение
```

Это не универсальность ради универсальности. Человек, который хочет YouTube в
туннеле, должен иметь возможность вставить адрес из адресной строки браузера — и
получить работающее правило, не изучая предварительно, что такое domain suffix.

**Три режима вместо действия по умолчанию.** Список правил сам по себе не
говорит, что с ним делать: одни и те же сто доменов означают «пускать в туннель
только это» или «пускать всё, кроме этого» — прямо противоположные вещи.
Раньше это выражалось настройкой «куда идёт трафик, не подошедший ни под одно
правило», и это оказалось неверной постановкой вопроса: она заставляет
пользователя рассуждать от остатка к замыслу, а не наоборот. Хуже того, в ней
легко застрять в состоянии, где VPN не делает ничего — именно это и случилось на
живом роутере. Подписка присылает список того, что должно идти **мимо** туннеля;
при действии по умолчанию «напрямую» такой список не меняет ровным счётом
ничего, и весь трафик спокойно идёт мимо VPN, притом что клиент показывает
«подключено», оба ядра работают и ни одной ошибки нигде нет.

Теперь режим называет замысел целиком:

| `config.SplitMode` | Смысл | Fallback |
|---|---|---|
| `proxy-list` | в туннель уходит только перечисленное | `direct` |
| `bypass-list` | в туннель уходит всё, кроме перечисленного | `proxy` |
| `off` | в туннель уходит всё, списки не читаются | `proxy` |

Действие для новой записи следует из режима и всегда противоположно fallback:
запись, совпадающая с ним, не способна изменить ни одного исхода. Записи, которые
после смены режима стали такими, интерфейс помечает «no effect», а не оставляет
молча лежать в списке.

Старое поле `default_action` читается при загрузке, переносится в `split` и
больше не пишется — конфигурация, написанная до этого разделения, не должна
менять маршрутизацию оттого, что её открыла новая версия.

**Три вещи, которые пришлось сделать правильно, а не очевидно.**

*Путь из URL выбрасывается, и об этом сообщается.* На зашифрованном соединении
роутер видит только адрес назначения и TLS-хендшейк, пути там нет физически.
Промолчать об этом — значит дать пользователю поверить, что он ограничил правило
уже, чем на самом деле.

*Суффикс раскрывается в две формы.* Ядро сравнивает строки, а не метки домена,
поэтому голый суффикс `youtube.com` совпал бы и с `notyoutube.com`. Честная
запись «этот домен и всё под ним» — это точное имя плюс суффикс с ведущей
точкой, и компилятор выдаёт обе.

*Порядок правил сохраняется при сжатии.* Побеждает первое совпадение, поэтому
группировать все записи по действию нельзя — это молча переставило бы их.
Схлопываются только **соседние** записи с одинаковым действием: результат от их
внутреннего порядка не зависит, а список пользователя обычно и есть одна длинная
серия «в туннель», так что сотня доменов становится одним правилом.

**Перекрытые правила.** Самая острая грань модели «первое совпадение» в том, что
она невидима, пока что-то не перестанет работать. Пользователь добавляет
`youtube.com → туннель`, потом `ads.youtube.com → блок` — и второе правило
мертво. `FindShadowed` находит такие случаи, отличает вредные (действия
расходятся) от просто избыточных и говорит, что переставить:

```
#6 ads.googlevideo.com — changes behaviour
   rule #2 (googlevideo.com) already matches everything #6 would,
   so traffic goes proxy instead of block
   fix: move #6 above #2
```

**Ограничение по клиенту.** У записи есть `Sources` — список адресов или подсетей
LAN. Это единственное измерение маршрутизации, которое есть у роутера и нет у
десктопного клиента: «телевизор через туннель, рабочий ноутбук нет» выразимо
только здесь.

**Проверка до применения.** `routing.Test` повторяет логику сопоставления ядра,
чтобы можно было узнать, что сделают правила, *до* того как их получит роутер, от
которого зависит весь дом.

## 8. Интерфейс: слой состояния, API, браузер

`internal/app` — единственный владелец running state. Через него проходит всё,
что меняет состояние, и именно поэтому браузер и командная строка оказываются
двумя видами на один демон, а не двумя программами, которые правят одни файлы.

`internal/api` — REST поверх `app`, плюс раздача самого интерфейса.

**Два замка, а не один.** `app.mu` защищает состояние в памяти и держится
ровно столько, сколько занимает чтение или запись поля. `app.applyMu`
сериализует медленную половину: запуск и остановку ядер, разрешение имён
серверов, установку правил firewall. Разделение не косметическое. Пока
`Connect` держал общий замок на всё время применения, любой запрос статуса
вставал в очередь за перезапуском ядра, а интерфейс замирал целиком.

Хуже была вторая половина той же ошибки. Горутина опроса счётчиков раз в секунду
зовёт `App` обратно, и этот вызов брал `app.mu`. Остановка опроса ждёт, пока
горутина завершится, и вызывалась она из-под `app.mu` — то есть демон ждал
горутину, которая ждала замок, который держал ждущий. Второе нажатие «подключить»
намертво вешало API: `/api/status`, `/api/rules`, `/api/settings` переставали
отвечать навсегда, поток событий замолкал, а снаружи это выглядело как «интернет
сломался». Теперь история живёт под собственным `histMu`, обратные вызовы не
касаются состояния вообще, а монитор снимается под замком и останавливается уже
без него. `internal/app/lock_test.go` проверяет именно это: вызов
`recordSample` при захваченном `app.mu` обязан вернуться.

**Изменения доходят до ядра сразу.** Правка правила или настройки пишется на
диск и тут же применяется к работающему туннелю через `App.Reload`. Без этого
интерфейс принимал правило, отчитывался об успехе и не менял ничего — правило
лежало в списке и вступало в силу только при следующем переподключении, что
пользователь никак не мог связать со своим действием. Дорого это не стоит:
`Runtime.Apply` хеширует конфиг каждого ядра и перезапускает только то, чей файл
действительно изменился. Ошибка применения не отменяет сохранение — правка
удалась, а невзятый ядром конфиг попадает в `last_error` на видное место.

**Почему SSE, а не WebSocket.** Поток здесь односторонний и редкий: «что-то
изменилось, перечитай». SSE — это HTTP-ответ, который не заканчивается: не нужна
библиотека, не нужен upgrade-хендшейк, не нужен пинг-цикл, а браузер сам
переподключается при обрыве. Событие несёт только тип изменения, не новое
значение — подписчик, пропустивший событие, догоняет на следующем, а не
рассинхронизируется.

**Аутентификация.** Токен обязателен: control plane VPN-клиента решает, куда
уходит трафик всего дома. Сравнение constant-time, чтобы неверный токен нельзя
было подобрать посимвольно по времени ответа. Токен принимается в заголовке, в
cookie и — только для потока событий, куда `EventSource` не умеет добавлять
заголовки — в query.

**Почему фронтенд без сборки.** Нативные ES-модули и CSS, никакого React и
никакого npm. Интерфейс вшивается в бинарник через `go:embed`: развёртывание
Obelisk остаётся копированием одного файла, в Docker-образ не приезжает
`node_modules`, а на Pi не тратится память на рантайм фреймворка. LuCI сделан так
же, и не от бедности.

Раздел сплит-туннеля — одно поле, куда вставляется что угодно, построчно. После
добавления интерфейс отчитывается, как понял каждую строку, и что именно
отбросил. Перекрытые правила показываются вместе с кнопкой «переставить выше»,
которая чинит проблему одним нажатием.

### DNS: четыре умолчания, каждое из которых ломало сеть

Всё ниже найдено на живом роутере по одному и тому же симптому — «включаю VPN,
интернет пропадает» — и ни одна из причин на этот симптом не похожа.

**Резолвер прямого пути не должен быть адресом этой машины.** sing-box с
`auto_detect_interface` привязывает исходящие сокеты к интерфейсу маршрута по
умолчанию — иначе его собственные соединения вернулись бы в туннель, который он
поднимает. Побочный эффект: всё, что недостижимо через этот интерфейс, недостижимо
и для ядра. Умолчанием было `udp://192.168.1.1` — адрес самого роутера, где
резолвер и правда живёт. С точки зрения ядра пакет туда уходит в WAN и вручается
провайдеру, где приватный адрес умирает. Ядро переставало разрешать имена вообще:
и на прямом пути, и — что хуже — имя того самого сервера, через который собиралось
туннелировать. `reachableFromCore` теперь отвергает такие адреса, а умолчание
публичное.

**FakeIP выключен по умолчанию.** Он нужен, чтобы доменные правила работали для
клиентов, отдающих роутеру только адрес. Но `action: sniff` уже достаёт имя из
TLS-хендшейка и заголовка Host, и это покрывает почти всё. Платит FakeIP дорого:
ответ клиента выбрасывается, и **каждое** соединение, включая прямое, ждёт второго
разрешения имени уже внутри ядра. Когда разрешение недоступно, ядро набирает
`198.18.x.x` буквально — в логе это выглядит как `dial tcp 198.18.0.3: i/o
timeout`, и связи с DNS на первый взгляд никакой.

**Запасной резолвер следует за трафиком.** Раньше `dns.final` был `dns-proxy`
всегда, если группа прокси существует. В режиме `proxy-list`, где через туннель
идёт только названное, это ставило разрешение имён всей сети в зависимость от
туннеля, которым эта сеть не пользуется, и добавляло круг до другой страны перед
каждым соединением. Теперь `final` определяется тем, куда идёт неподошедший
трафик, а имена, которые пойдут через прокси, разрешаются через него —
DNS-правила строятся из тех же маршрутных правил, а не декларируются.

**Туннель не объявляет IPv6, которого нет.** tun-интерфейс с IPv6-адресом ставит
IPv6-маршрут по умолчанию там, где его не было, и с этой секунды каждое
двухстековое имя пробуется сначала по IPv6 — в туннель, у которого на прямом
выходе никакого IPv6 нет. Соединение падает за миллисекунды, а не по таймауту,
поэтому не выглядит сетевой проблемой и исчезает ровно при выключении VPN.
`hasGlobalIPv6` смотрит, есть ли у хоста собственный глобальный IPv6 (ULA и
link-local не в счёт — ULA как раз и раздаёт сам туннель), и при его отсутствии
интерфейс строится IPv4-only, а стратегия DNS становится `ipv4_only`.

## 9. Firewall: как перехват доходит до системы

`internal/netfw` применяет правила nftables и policy routing для режимов TPROXY и
REDIRECT. В режиме TUN он не делает ничего: sing-box сам ставит маршруты через
`auto_route`, и второй набор правил только дрался бы с первым.

**Два обязательства, оба из разбора сосуществования с zapret.**

*Obelisk владеет ровно одной таблицей и не трогает чужие.* Никакого
`flush ruleset`, никаких правок fw4, никаких допущений о том, что ещё висит на
тех же хуках. nftables вычисляет цепочки по приоритету, поэтому zapret, fw4 и
Obelisk уживаются. Флаш при старте был бы самым быстрым способом сломать роутер.
Это зафиксировано тестом, который проверяет отсутствие `flush ruleset` и любых
упоминаний чужих таблиц.

*Правила рендерятся отдельно от применения.* `Render()` детерминирован и не имеет
побочных эффектов — на нём стоят тесты, и он же отдаётся через `GET /api/firewall`.
Правила, стоящие между домом и интернетом, можно прочитать до того, как они
попадут на машину, которая является единственным выходом в сеть.

**Две метки, и они обязаны различаться.** `BypassMark` (`0x4f42`) ставят на свои
сокеты оба ядра — sing-box через `route.default_mark`, Xray через
`streamSettings.sockopt.mark`. Помеченное никогда не перехватывается: иначе
соединение ядра до сервера уходило бы в тоннель, который оно устанавливает.
`TProxyMark` (`0x4f43`) ставим мы, и по нему `ip rule` уводит пакет в отдельную
таблицу с `local default dev lo` — без этого ядро не считает пакет локально
адресованным и TPROXY не отдаёт его сокету.

Обе метки настраиваются: у zapret, например, заняты `0x40000000` и `0x20000000`.

**Непересечения меток недостаточно, и это пришлось узнать на живом роутере.**
Ранее здесь стояло, что раз метки не пересекаются и хуки не спорят, то zapret и
Obelisk уживаются. Биты действительно не пересекаются. Уживаются они всё равно
плохо, и вот измерение, одно и то же скачивание с одного и того же клиента:

| | 10 МБ через cloudflare |
|---|---|
| туннель выкл, zapret вкл | 10 000 000 Б @ 8.7 МБ/с |
| туннель вкл, zapret вкл | **21 102 Б @ 844 Б/с** |
| туннель вкл, zapret выкл | 10 000 000 Б @ 9.2 МБ/с |
| туннель выкл, zapret выкл | 10 000 000 Б @ 8.4 МБ/с |

По отдельности оба безупречны и уничтожают друг друга в сочетании. Механизм: в
режиме TUN каждое соединение LAN терминируется передним ядром, которое открывает
своё собственное наружу. `postnat_hook` у zapret пропускает всё, у чего снят бит
`0x40000000`, — а `0x4f42` его не несёт, поэтому соединения ядра попадают в
`nfqws`, и тот применяет к ним `dpi-desync=fake`, вбрасывая поддельные сегменты в
поток, порождённый userspace-стеком, а не ядром системы. Ломаются передачи к
хостам из hostlist zapret; к остальным — нет. Поэтому отказ и выглядит как «часть
сайтов открывается наполовину», а не как сломанная сеть: kernel.org в списке нет
и он ехал на полной скорости, пока cloudflare умирал на 21 килобайте.

**Настоящая причина оказалась глубже, и решение лучше.** Прятать ядра от zapret
работало, но ценой его отключения на прямом пути. Дальнейший разбор показал, что
ломалось вовсе не то, что мы думали: `speed.cloudflare.com` в hostlist zapret
вообще нет, то есть десинхронизации этого хоста не было — а передача всё равно
умирала.

Механизм в другом. `nfqws` вбрасывает поддельные пакеты через raw-сокет, то есть
они **локально порождённые**. А `auto_route` у sing-box ставит правило
`from 0.0.0.0 iif lo lookup 2022` именно для того, чтобы ловить локально
порождённый трафик до выбора адреса источника. Фейки zapret проваливались в
туннель вместо провайдера: DPI их не видел, обход молча не работал, а реальное
соединение оставалось наполовину рассинхронизированным и вставало.

Лечится одним правилом маршрутизации:

```
ip rule add pref 8900 fwmark 0x40000000/0x40000000 lookup main
```

`0x40000000` — это `--dpi-desync-fwmark`, которым zapret метит всё, что порождает
сам. Правило стоит выше диапазона 9000, где живут правила sing-box, и выпускает
эти пакеты обычным маршрутом. Конфигурация zapret не трогается ни в одном байте —
это чистая маршрутизация, и снятие правила возвращает систему ровно в исходное.

Измерение трёх режимов на одном наборе, туннель поднят, zapret работает:

| | `share` | `exempt` | `off` |
|---|---|---|---|
| discord.com (в hostlist zapret) | **200** | 000 | 000 |
| discordapp.com | **301** | 000 | 000 |
| cloudflare 10 МБ | **10 000 000 Б** | 10 000 000 Б | 21 740 Б |
| yandex.ru / mail.ru / 2ip.ru | ok | ok | ok |

`share` — единственный режим, где работает и то, и другое, и он стоит
умолчанием. Разделение труда получается естественным: zapret держит прямой путь
и остаётся быстрым, туннель берёт то, что zapret не вытягивает, и ни один из них
не требует настройки под другой. `netfw.DetectZapret` ищет таблицу `inet zapret`
по точному имени — «zapretx» принадлежит кому-то другому, и молча освобождать
чужой фаервол от своих правил недопустимо.

`exempt` оставлен как безопасный запасной вариант, `off` — для будущего zapret,
которому ничего этого не понадобится.

**Что всегда в обходе.** Зарезервированные диапазоны (LAN, loopback, multicast —
их перехват отрезал бы роутер от устройств, которые он обслуживает), плюс адреса
самих серверов из подписки, плюс пользовательский список.

**QUIC в режиме REDIRECT.** REDIRECT физически не умеет перехватывать UDP.
Поэтому есть опция отклонять UDP/443, чтобы браузер откатился на TCP. Без неё
QUIC уходит мимо туннеля, а пользователь видит работающее соединение — худший
вид отказа для инструмента приватности, потому что он невидим.

**Порядок операций.** Правила ставятся только после того, как ядра начали
слушать, и снимаются раньше, чем ядра останавливаются. Иначе трафик LAN уводился
бы на порт, за которым никого нет. Если установка сорвалась на середине, всё
откатывается: наполовину применённый набор оставил бы дом без выхода в сеть.

**Уборка за убитым туннелем.** Худший отказ, который этот продукт способен
устроить, выглядит так: sing-box в режиме TUN ставит свои `ip rule` в диапазоне
9000–9010, направляющие весь LAN в таблицу 2022. При штатной остановке он их
снимает. При убийстве — OOM, просроченный таймаут остановки, `docker kill`,
выдернутый шнур — не снимает никто. Остаётся набор правил, гонящий весь дом в
таблицу, где нет ни одного маршрута, и нет интерфейса, который бы его нёс.
Каждый клиент молча теряет интернет, сам роутер продолжает работать, потому что
подходит под другое правило, и нигде не появляется ни единой ошибки.

`netfw.Sweep` разбирает это при старте демона и после каждого отключения. Две
детали пришлось добавить после того, как первая версия уборки уже стояла, а
роутер всё равно остался без сети:

*Интерфейс исчезает не мгновенно.* tun-устройство уходит, когда отпущена
последняя ссылка на него, — заметно позже, чем убит державший его процесс.
Уборка, запущенная в первую секунду жизни демона, видела интерфейс на месте,
заключала, что туннель жив, и уходила. Теперь она ждёт его исчезновения, но
только если в диапазоне вообще есть что убирать — на чистой системе она
возвращается сразу.

*Правило само говорит, что осиротело.* Ядро печатает `[detached]` у правила,
ссылающегося на несуществующий индекс устройства. Это доказательство сильнее
`ip link`, и по нему уборка срабатывает не дожидаясь таймера.

Живой туннель при этом не трогается ни при каких условиях, и `orphan_test.go`
проверяет отдельно и это, и обе детали выше.

### Проверка доступности: два вопроса, а не один

«Работает ли интернет» и «работает ли VPN» — разные вопросы, они отказывают
независимо, и лечатся противоположно. Роутер с упавшим каналом и роутер с
неправильно настроенным туннелем из браузера выглядят одинаково, а единственная
лампочка «подключено», которую показывает любой VPN-клиент, сообщает лишь то, что
процесс запущен, — не то, что трафик куда-то доезжает.

Поэтому проверок две, с разными наборами:

*Интернет* спрашивается у ресурсов, которые не блокируют — `yandex.ru`,
`mail.ru`, `2ip.ru`. Проверять здесь зарубежный сайт значит получать ложную
тревогу на каждой цензурируемой сети.

*Туннель* спрашивается у ресурсов, которые заблокированы точно — `telegram.org`,
`rutracker.net`, `meduza.io` — и запрос идёт **через SOCKS самого ядра**. Это и
есть смысл: достижимый хост не доказал бы ничего, а заблокированный отвечает
только если трафик действительно ушёл в туннель. Ответ 403 засчитывается —
challenge-страница доказывает, что соединение дошло; понравился ли клиент сайту,
вопрос другой.

## 10. Измерения: задержки и трафик

`internal/probe` берёт и то и другое из Clash API sing-box, а не измеряет само.
Это осознанно: фронтовое ядро уже знает все узлы, уже держит к ним пул соединений
и уже считает байты. Открывать собственные сокеты означало бы мерить не тот путь,
по которому идёт трафик, и получать цифры, расходящиеся с реальностью ровно в тех
случаях, когда это важнее всего.

Узлы на Xray покрыты тоже: для фронтового ядра это обычные SOCKS-аутбаунды, и
замер через такой измеряет всю цепочку — то есть именно то число, которое
интересует пользователя.

**Опрос вместо потока.** У контроллера есть стриминговый `/traffic`, но
`/connections` за один запрос отдаёт кумулятивные счётчики, число соединений и —
через разность — скорость. Никакого долгоживущего потока, который надо
переподключать и не течь им.

**Ноль миллисекунд — это не «мгновенно».** Провалившийся замер контроллер
возвращает нулём. Показать его как `0 ms` означало бы поставить мёртвый узел в
начало списка как лучший; поэтому есть отдельный флаг «измерялся», и такой узел
подписан `unreachable`.

**Параллелизм ограничен восемью.** Не из вежливости: сотня одновременных
TLS-хендшейков на слабом процессоре роутера душит трафик, который через него идёт,
и замеры возвращаются искажёнными той нагрузкой, которую сами и создали.

**Переключение узла роняет соединения.** Иначе выбор применился бы только к новым,
и пользователь, сменивший узел из-за отказов, продолжал бы смотреть на отказы.

## 11. История и цена, которую она стоила

`internal/store` — SQLite через `modernc.org/sqlite`, чистый Go. Любая другая
привязка требует cgo, а cgo убил бы кросс-компиляцию.

**Свёртка вместо накопления.** Каждая запись сразу попадает в три разрешения —
минуты, часы, дни. Не отложенным rollup'ом, а прямо на входе: нет фонового
задания, которое надо планировать, и нет окна, когда час пуст, потому что
свёртка ещё не отработала. Хранение — минуты сутки, часы месяц, дни год. Это
около 2500 строк, килобайты. Простои не пишутся вовсе: роутер простаивает
бо́льшую часть времени, и строка в секунду на нули забила бы базу пустотой.

**Средняя задержка считается только по успешным попыткам.** Учитывать провал как
ноль означало бы утянуть среднее вниз и выдать ненадёжный узел за самый быстрый.
Доля отказов отдаётся отдельным числом — это честный способ сказать «быстрый,
когда работает, а работает не всегда».

**А теперь цена.** `modernc.org/sqlite` не поддерживает 32-битные ARM и MIPS.
Добавление зависимости сломало сборку под `linux/arm`, `linux/mips` и
`linux/mipsle` — а armv7 это не экзотика, это огромная доля роутеров и цель с
первого дня проекта.

Терять три архитектуры ради графиков — плохой размен. Поэтому опциональной стала
история, а не архитектура: пакет собирается в двух вариантах через тег
`nosqlite`, `Makefile` подставляет его автоматически для затронутых целей. В
таком билде работает всё — подписки, маршрутизация, оба ядра, firewall, живой
трафик и задержки, — нет только долгосрочных графиков. Вызывающий код не
изменился ни на строку: неудача открытия истории и раньше была штатной ситуацией,
потому что файловая система может оказаться readonly.

| Цель | Размер | История |
|---|---:|---|
| linux/amd64, arm64, riscv64, 386 | 11–12 МБ | есть |
| linux/arm, mips, mipsle | 7.8–8.8 МБ | нет (`-tags nosqlite`) |

## 12. Что сделано и что дальше

**Готово:** модель узла и матрица возможностей; парсеры всех перечисленных
форматов с тестами; генераторы конфигурации обоих ядер; планировщик топологии с
мостами; supervisor процессов с экспоненциальным backoff и кольцевым буфером
логов; runtime, применяющий план и перезапускающий только то ядро, чей конфиг
реально изменился; установка и обновление ядер с откатом; движок маршрутизации с
разбором пользовательского ввода, компиляцией и поиском перекрытых правил;
персистентная конфигурация; слой состояния, REST API с SSE и аутентификацией;
веб-интерфейс, вшитый в бинарник; firewall-слой для TPROXY и REDIRECT с обходом
по метке, блоком QUIC и kill-switch; замеры задержек и живая статистика трафика;
история в SQLite со свёрткой и удержанием; CLI `parse` / `plan` / `generate` /
`run` / `daemon` / `core` / `route`; Docker-образ multi-arch.

**Дальше — только проверка на живом железе:** сборка Docker-образа и применение
правил nftables к настоящему netfilter. Тестами покрыт их рендер, а не поведение
ядра, и это единственное существенное белое пятно.

Нативный ipk из плана исключён по решению владельца проекта.

## 10. Открытый вопрос: валидация против реальных ядер

Конфигурация, которую Obelisk считает правильной, остаётся гипотезой, пока с ней
не согласится ядро, которое обязано её прочитать. Схемы обоих ядер живые: sing-box
переработал DNS-серверы в 1.12 и перенёс WireGuard в `endpoints` в 1.11, Xray
переименовал `tcp` в `raw` и добавил `listen` в объект `metrics`.

Поэтому `obelisk generate` заканчивается прогоном `sing-box check` и
`xray run -test` по сгенерированным файлам, и отсутствие бинарника отчитывается
как «проверка не выполнена», а не как «проверка пройдена». Непройденная проверка
ничего не доказывает.

Целевые версии: **sing-box ≥ 1.12** (проверено против 1.13.16), **Xray ≥ 25.x**
(проверено против 26.3.27). Xray использует календарные версии, не семантические,
поэтому «1.8.x» и «26.x» — это не откат, а смена схемы нумерации.
